# WebView 重构剩余问题：第三轮整改目标

> 依据：第三轮静态审查（截至 2026-10-15）。本文件是对 `docs/webview-review-remediation.md` 的收尾补充，仅处理下面两项未关闭的问题。未执行 Windows 实机验证，风险不等于已复现故障。

## 结论与边界

保留目前的 WebView、HTTP API、Runtime、托盘和单实例架构。此前 WebView 启动异常回退已通过静态审查，本轮不再重做。**仅修正关闭确认竞态与安装恢复的不完整性，不追加其他功能、抽象或重构。**

## P2-1：关闭确认的过期 ACK 可能清除新请求

### 证据

- `Runtime.request_close_prompt()` 只设置布尔状态；`acknowledge_close_prompt()` 不带请求身份，直接清零。
- `app/app.js` 收到 `close_prompt` 后发送 `POST /api/window/close/ack`，未附对应请求标识。
- 若请求 A 的 ACK 延迟，期间用户取消弹框并再次点击关闭产生请求 B，迟到的 A-ACK 可能清除 B。

### 整改目标

- 每次关闭请求具有明确、可比较的身份（例如递增序号）；前端确认时必须携带当次身份。
- 仅允许与当前待处理请求匹配的 ACK 清除该请求。重复或过期 ACK 应无害、幂等。
- 其他状态请求不能消耗关闭事件；页面刷新、长轮询重连后仍可恢复未确认的请求。
- 用户选择“退出”或“隐藏到托盘”、记住选择、取消弹窗等现有行为不变。
- 如要严格满足“仅目标 WebView 可确认”，应明确窗口身份边界；可以先采用最小方案，避免引入额外消息系统。

### 必须验证

- A 发出后，B 发出，再提交 A 的 ACK：B 仍处于待确认状态。
- 对 A 重复 ACK、错误身份 ACK：不得误清除 B。
- 正确 ACK B 后事件才消失；刷新/重连读取一致。
- 连续点击关闭、取消后再次关闭、多个状态读取者并发时，弹窗与确认行为正确。
- 添加针对 `runtime.py`、`server.py`、`app/app.js` 协议一致性的测试，避免只测试布尔值。

## P1-2：安装回滚遗漏新增文件，且当前失败测试可能未进入覆盖阶段

### 证据

- `installer.pyw` 备份旧版已有文件；失败时 `_restore_program_files()` 只复制备份内容，没有删除升级中新创建的程序文件。
- `tests/test_installer.py` 的故障注入以 `shutil.copy2` 调用次数计数；备份阶段本身也调用 `copy2`，因此测试可能在实际覆盖之前就失败，不能证明“部分覆盖后的恢复”。

### 整改目标

- 升级开始前记录原程序文件/静态资源的存在状态；失败恢复时还原旧文件，并清除仅由本次升级添加的新程序文件。
- 恢复范围严格限定于已知安装程序文件和 `app/` 静态资源。**绝不删除或重置** `config.json`、`library/`、`cache/`、`logs/`、`runtime/` 等用户及运行时数据。
- 备份失败不得开始覆盖；临时目录的创建、清理及失败消息与实际结果一致。
- 恢复不完整时明确报告残留风险，不能把“尽力恢复”报告成完整回滚。
- 不引入通用安装事务框架；使用明确的安装清单/快照和小范围回滚机制。

### 必须验证

- 先确保至少一个目标程序文件**确实已被新版本覆盖**，再在后续复制点注入 I/O 失败；验证旧内容恢复。
- 旧版本缺少的新文件已部分复制后失败：这些新文件必须被清除。
- `app/` 中新增加的静态资源已复制后失败：只移除新增资源，保留原有静态资源。
- 备份阶段失败：目标程序目录完全不被修改。
- 恢复本身失败：报告不完整恢复，并保留可调查的错误信息。
- 用户配置、图库、缓存、日志、运行时数据全部保留。
- 继续验证升级前运行实例复查有效；但不要求本轮扩展到完整跨进程锁或新的安装器体系。

## 执行与停止条件

1. 首先检查最新源码确认缺陷仍在；如推断不成立，用证据说明，不为满足文档而改代码。
2. 先让上述关键失败场景在测试中真实触发，再实施最小修复。
3. 执行相关测试及全量回归测试；在提交说明中区分实际执行结果、静态推断和未验证项。
4. 涉及 Windows 安装与 WebView 事件的场景尽可能实机检查；未检查就明确写“未验证”。
5. 两项整改通过后，**停止本轮整改**。不延伸到 UI、美化、业务逻辑、框架替换或新的架构设计。
