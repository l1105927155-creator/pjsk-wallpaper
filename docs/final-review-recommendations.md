## 结论

本轮不需要继续进行架构重构。以下三项原审查问题已按目标修复，可从本轮整改范围关闭：

- 缩略图缓存键碰撞、并发生成与临时文件竞争。

## 剩余问题与整改目标

### 1. P2：检查与复制之间存在竞争窗口

**依据：** `installer.pyw` 在向导「下一步」时调用 `_confirm_not_running(dest)`，随后才创建执行 `_install(dest)` 的后台线程。检查之后、文件复制之前，应用可能重新启动。

**目标：**

- 在真正修改程序文件前再次核对目标安装实例状态；检查不通过则停止复制并给出可操作提示。
- 不通过杀进程、猜测浏览器窗口是否关闭来判断实例状态。
- 应认识到二次检查只能缩小时间窗口，不能提供严格排他保障。如果需要彻底消除竞争，可采用与启动器协调的、范围有限的升级排他机制；不要为此引入通用锁服务。

**验收：** 构造「向导检查通过后、复制开始前启动后台实例」的情形，确认安装器不会继续覆盖程序文件。

### 2. P2：升级中途失败可能留下混合版本

**依据：** `installer.pyw` 仍按文件/目录逐项覆盖安装目录，出现复制失败时仅提示可能不完整，没有恢复旧版本的机制。

**目标：**

- 在修改现有程序文件前完成新程序文件的预检查/暂存，并对将要替换的原程序文件创建可恢复备份。
- 替换失败时尽最大可能恢复原程序文件，同时完整保留 `config.json`、`library/`、`cache/`、`logs/` 等运行数据。
- 恢复失败时明确告诉用户目录可能不一致及可行的恢复方式；不能错误报告安装成功。
- 优先采用简洁的暂存、备份和失败恢复方案，而不是引入安装事务框架。

**验收：** 故意在复制中途制造 I/O 失败，验证旧版程序文件可恢复，个人配置与图库内容不变，且提示结果与真实状态一致。

## 实施边界

1. 先核对当前源码及测试是否仍符合本报告的前提，必要时用失败测试确认风险。
2. 仅修改安装/升级相关代码及其测试；如确有必要，可对启动器增加少量配合逻辑。
3. 避免额外的模块拆分、依赖、UI 修改与业务功能变更；不要重开已通过的三项问题。
4. 分别运行安装器相关测试和原有全量回归测试，并记录真实执行结果。
5. 在 Windows 实机覆盖「后台运行但 Web 窗口已关闭」「正常退出后升级」「无实例首次安装」「升级中途失败」「升级后数据保留」场景。无法实机验证必须明确标注未验证。
