# Web 重构代码审查与整改目标

> 审查范围：Web UI 重构后的 `main` 分支；静态代码审查，未在 Windows 上复现问题。  
> 目的：解决可验证的可靠性风险，不启动新一轮架构重构。

## 总体判断

目前的方向正确：`runtime.py` 负责调度，`server.py` 提供本地 HTTP API，`launcher.pyw` 负责生命周期，Web UI 仅承担交互。保留此职责分工，优先完成以下四项整改。

下述 P1/P2 代表整改优先级，**不是已经实机复现的故障结论**。Agent 开始修改前应先核对当前代码、补充可以复现问题的测试；如果审查推断与实现不符，应说明证据并调整范围。

## P1-1：配置读改写并发一致性

**涉及：** `runtime.py` 的 `Runtime.apply_config()`、`start_update()`，以及 `core.config_save()`。

**审查依据：** `apply_config()` 先在锁内复制配置，在锁外校验，随后整体替换；持久化在锁外执行。并发 PATCH、图库更新触发时的保存可能造成丢失更新或共享 `config.json.tmp` 竞争。

**整改目标：**

- 不同线程修改不同配置字段时互不覆盖；更新运行时间等内部字段也不得被旧配置快照回写。
- 配置状态发布、校验及持久化具备明确的一致性和失败语义。不能对客户端报告保存成功，却让内存与磁盘状态不一致。
- 多个写入者不能同时竞争同一个临时文件；仍保留原子替换文件的行为。
- 保留现有配置字段、合法范围、导入/导出语义，不改变业务规则。

**验收：** 添加并发修改两个独立字段、配置修改与图库更新同时保存、磁盘写入失败的测试；最终内存及磁盘值一致，未出现无提示的丢失更新。

## P1-2：缩略图缓存并发与缓存键

**涉及：** `core.thumbnail()`，及多请求预览缩略图场景。

**审查依据：** 同一缩略图使用固定 `.tmp` 文件；缓存键由 `path.stem`、文件修改时间、宽度构成，未明确区分不同图库路径。并发写和同名图片可能碰撞。

**整改目标：**

- 同一图片相同尺寸的并发请求不产生临时文件竞争或损坏。
- 不同来源/目录的同名图片不能误用彼此缓存。
- 图片内容更新后缓存按合理规则失效；缓存生成失败不污染可用缓存。
- 保持缩略图按需加载，不引入无必要的缓存服务或数据库。

**验收：** 并发请求同一图；不同来源同名、相同修改时间的两张不同图片；图片更新后重新获取；生成失败后重试。检查内容正确、无残留损坏文件。

## P2-1：HTTP 查询参数的错误处理

**涉及：** `server.py` 的 `/api/gallery`、`/api/gallery/update/log` 等参数解析入口。

**审查依据：** 部分参数直接调用 `int()`，非法输入可能将异常抛出到请求线程，而非返回明确的客户端错误。

**整改目标：**

- 对分页偏移、每页数量、日志行数等参数统一校验类型、范围和上限。
- 非法输入返回 HTTP 400 与一致的 JSON 错误，不中断服务。
- 大数、负数、空值、非整数与重复参数有确定行为，不引入不必要的通用校验框架。

**验收：** 覆盖正常值与无效值（如 `offset=abc`、负数、超限数字）；服务继续能响应后续正常请求。

## P2-2：安装升级与运行实例协调

**涉及：** `installer.pyw`、`launcher.pyw`、相关安装/启动入口。

**审查依据：** 安装器当前直接复制到目标目录；关闭浏览器 UI 不代表后台服务已退出。运行中的实例可能继续使用旧模块，同时磁盘文件已更新。

**整改目标：**

- 升级已有安装目录之前检测本应用后台实例，明确提示并要求正常退出后才覆盖程序文件；不依据“浏览器窗口是否关闭”判断进程退出。
- 检测与关闭操作不能误杀无关进程；实例无法安全退出时停止升级并告知原因。
- 保留 `config.json`、`library/`、`cache/` 和用户日志；升级失败尽量不留下不可运行的混合版本。
- 安装器、快捷方式、开机自启、托盘退出的既有功能保持不变。

**验收：** 在后台运行且关闭 Web 窗口时升级；正常退出后升级；没有实例时安装；升级失败；已有图库与设置保留。以上须在 Windows 实机测试，不能仅凭 mock 单测通过视为完成。

## 执行要求

1. 先读取当前源码、测试及 `docs/architecture-refactor.md`、`docs/ui-refactor.md`；确认本报告中的风险在当前版本仍成立。
2. 按上述四项逐个整改，尽量先写失败测试，再进行最小修复，并运行现有回归测试。
3. 对必须通过 Windows API 验证的部分进行实机验收；无法执行时标明“未验证”，不得以推测冒充通过。
4. 每项在提交说明中写明：发现的问题、修复方式、对应测试与未覆盖风险。
5. **不做**额外的技术栈迁移、模块拆分、UI 重设计、业务规则重定义或新功能开发。若发现更严重但不在本报告内的问题，先报告证据和影响，再决定处理范围。

- [ ] 无效 HTTP 参数稳定返回结构化错误，后续请求不受影响。
- [ ] 安装升级不会静默覆盖仍在运行的程序，既有数据完整。
- [ ] 全部现有测试无回归；Windows 相关场景的实机验证结果有记录。
